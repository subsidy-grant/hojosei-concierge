# Error-rewrite エラーメッセージ全数書き換えループ

**エラーが出た瞬間こそ利用者が一番困っている瞬間。**その時に出る文章を全数、非IT利用者（美容室スタッフ・中高年含む）が読んで次の行動が分かる状態にする。

## 手順

1. **範囲を確定**（指定がなければ現リポジトリのユーザー対面部分。除外があれば編集前に明示）。
2. **エラー文言の全数棚卸し**：
   - ソースコード内のエラー文字列（throw、alert、toast、validation）
   - APIやLINE応答として表面化するエラー
   - 実ブラウザで到達できるエラー状態（未入力、通信断、権限なし、空データ）
3. **台帳を作る**（`error-inventory.md` に表形式）：場所／発生条件／現在の文言／利用者への害／置き換え案／実装状況／検証結果。
4. **利用者への害の大きい順に並べる**（例：高＝何が起きたか分からず作業が止まる・誤操作を誘発／中＝分かるが不親切／低＝表現の好み）。
5. **1グループずつ書き直す**。日本語の文言基準：
   - **何が起きたか**を平易に＋**次に何をすればいいか**を1行で（例：「保存できませんでした。電波の良い場所でもう一度お試しください」）
   - 専門用語・英語エラー・コード番号だけの表示を残さない
   - **内部情報を出さない**：プロバイダ名（Supabase等）・スタックトレース・内部ID・実装詳細は画面に出さず、ログにだけ残す
6. **変更ごとに検証**：関連テスト実行＋可能な限りPlaywright実ブラウザで該当エラー状態を実際に発生させて表示を確認。修正後に生のエラー文字列が残っていないか再検索。

## 停止条件

- 台帳の全行が「検証済み」または「ブロック（理由付き）」になった（正常終了）
- **到達手段のないエラー状態を「検証済み」と書かない**——到達不能なら「未検証・到達不能」と記録

## 禁止事項

- スクリーンショットなしの「直しました」報告
- 文言を綺麗にするために情報を削りすぎて「エラーです」だけにする
- ログから技術詳細を消す（画面から消す、ログには残す）

## 報告形式

「台帳（全行のステータス付き）／変更ファイル一覧／テスト結果／実ブラウザのビフォーアフター（実行時刻付き）／ブロック項目」。
