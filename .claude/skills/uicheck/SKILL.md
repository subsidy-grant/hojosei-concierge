# Uicheck 初見完走＋UI採点の統合検証ループ

**1周のクリーンセッション走査で2つを同時にやる**：①初見ユーザーとして完走できるか（導線の欠陥）②各画面が良いか（品質の採点）。

## 手順

1. **対象フローと完了基準を決める**（例：「診断開始→結果表示まで」）。指定がなければ製品の主要フローを推奨として選ぶ。
2. **クリーンな実ブラウザで開始**：Playwright（python3、chromium同梱）で保存ログイン・Cookie・localStorage・キャッシュなしの新規コンテキスト。**本物の入口**（公開URL・QRコード）から。開発者しか知らないURL直開きは不可。**毎周これをやり直す**。
3. **初見ユーザーとして走査**：画面に見えている案内だけを頼りに完走を試みる。つまずきをすべて記録（次に何をすればいいか分からない箇所／専門用語の要求／初回だけ発生するエラー・空状態の崩れ）。経験者の記憶で補完しない（利用者は美容室スタッフ・中高年含む非IT層という前提）。
4. **同じ走査中にスクリーンショット取得と採点**：スマホ幅375pxとPC幅1280pxで意味のある画面（初期・入力中・結果・エラー）をすべて撮り、統一チェックリストで各5点満点採点：
   - **視覚的階層**：最初に目が行く場所が、その画面の最重要アクションか
   - **一貫性**：色・余白・ボタン形状・用語が画面間で揃っているか
   - **可読性**：フォントサイズ・コントラスト（4.5:1目安）・行間。非IT・中高年でも読めるか
   - **操作性**：タップ領域44px目安、入力の手間、エラー時に次の行動が分かるか
   - **状態表現**：ローディング・空状態・エラー・成功が視覚的に分かるか
   - **キーボード・ズーム耐性**：Tab移動で操作できるか、200%ズームで崩れないか
5. **修正は優先順位付きで1周1件**：
   1. **完走を妨げる障害**（最悪のものから）— これがある限り採点改善より優先
   2. 障害ゼロなら**最弱スコアの改善**
   いずれもセキュリティ・アクセス制御・機能・既存の合格画面を壊さない最小変更で。
6. **セッションを破棄して最初から再走・再採点**。修正箇所以外のスコアが下がったり新たな障害が出たら、その変更は破棄する（regression-freeのみ残す）。

## 停止条件

- **中断なし完走＋全画面が目標スコア以上**を達成（正常終了）
- **2周連続で改善なし**（伸び止まりとして正直に記録）
- 安全な修正が存在しない／アクセス遮断／承認が必要な変更に到達

## 禁止事項

- クリーン化の省略（前回のlocalStorageが残った走査は無効）
- スコアや完走のために基準・セキュリティ・要件を緩める
- スクリーンショットなしの「改善しました」報告

## 報告形式

「辿った経路／障害一覧（深刻度順、解消済み・未解消を区別）／画面×項目のスコア表（改善前→後）／ビフォーアフターのスクリーンショット（実行時刻付き）／破棄した変更と理由／停止理由」。

## 他スキルとの分担

- **artdirection**（作る前）= どんな見た目にするか決める。uicheckの採点でシグネチャ要素が可読性・操作性を壊していると出たら可読性を優先
- **uicheck**（作った後）= 完走できるか＋良いか、を1周で検証・改善
