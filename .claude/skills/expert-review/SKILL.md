# Expert Review 3専門家並列レビュー

3人の専門家サブエージェントを**並列**で起動し、コード品質をレビューする。**読み取り専用**——このスキル自体は修正しない（修正は結果報告後、本人の指示で）。

## 対象範囲の決定

1. 引数があればそのパス／機能を対象にする。
2. なければ `git diff` と直近のコミットから**今回の開発で触った範囲**を特定する。
3. gitがない場合や範囲が不明な場合はプロジェクト全体（ただし生成物・ライブラリ・`node_modules` は除外）。

対象ファイル一覧を確定してから、**3つのAgentを1つのメッセージで同時に起動する**（順次実行しない）。

## 専門家の担当と線引き（指摘の重複を防ぐため厳守）

### ① 基本品質レビュアー — 「表記の正しさ」
- 誤字脱字（コメント・UI文言・変数名のタイポ、日本語文言の誤り）
- 命名規則の統一（camelCase/snake_case混在、ファイル名の規則）
- コーディングスタイル（インデント・引用符の統一、未使用変数・import、デッドコード）
- コメントの鮮度（コードと食い違った古いコメント）
- **口を出さない領域**：構造の良し悪し、名前の「意味」の適切さ

### ② アーキテクチャレビュアー — 「構造」
- 責務の分離（1つの関数/ファイルが複数の仕事をしていないか）
- 依存の向き（UI層がデータ層の内部詳細を直接触っていないか、循環依存）
- SOLID違反のうち実害のあるもの（巨大関数、重複ロジック、変更に弱い箇所）
- 設定・定数のハードコード散在
- **口を出さない領域**：表記の統一、業務用語の対応。理論的正しさより「次の変更が楽になるか」で判断する
- **規模への配慮**：小規模プロジェクトに過剰な抽象化を要求しない。「今のままで問題ない」も正当な結論

### ③ ドメインレビュアー — 「意味」（軽量版DDD）
- ユビキタス言語：業務用語（タスク・担当者・催促・助成金・診断など）とコード内の名前が一致しているか
- 同じ概念に複数の名前が付いていないか（例：催促が reminder / notification / push に分裂）
- 逆に、別の概念が同じ名前を共有していないか
- 機能の置き場所：この業務ルールはなぜこのファイルにあるのか説明できるか
- **口を出さない領域**：表記規則、レイヤー構造。境界づけられたコンテキスト等の本格DDD概念はプロジェクトが複数チーム・複数モジュール規模になるまで持ち出さない

### 全員共通の禁止事項
- **バグ探しをしない**（正しさの検証は /code-review と /slice の検証工程の担当）
- 修正しない（読み取り専用）
- 指摘には必ず「ファイル:行」と根拠を付ける。一般論だけの指摘は出さない

## サブエージェントへの指示に含めること

各エージェントに：対象ファイル一覧、上記の担当と線引き、禁止事項、および出力形式——
「指摘ごとに: 重大度（高=放置すると変更コストが増え続ける／中=次に触るとき直すべき／低=好みの範囲）、ファイル:行、内容、修正案の1行要約」を渡す。**問題がなければ「なし」と正直に返す**よう明記する。

## 統合レポート（本人向け）

3つの結果が揃ったら：
1. 同一箇所への指摘をマージ（重複はどちらの観点か明記して1件に）
2. **重大度順**に並べる（専門家別ではなく、全体を横断して）
3. 各指摘に「どの専門家」「ファイル:行」「修正案」を付ける
4. 最後に「今すぐ直すべき高のみ／全部直す／直さない」の推奨を1つ提示して**停止**（修正は始めない）

指摘ゼロの観点も「①基本品質：指摘なし」と明示する（レビューしなかったのと区別するため）。
