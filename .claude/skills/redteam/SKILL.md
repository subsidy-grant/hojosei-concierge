# Redteam 設計批判ループ

設計を確定する**前**に、批判役として「この設計は間違っている」という立場から異議を挙げ、建設役がそれを潰すか受容するまで回す。

## 手順

1. 対象の設計（アーキテクチャ／画面フロー／公開計画／データ構造）を1段落で要約し、本人に見えるようにする。
2. **批判役**として異議を挙げる。各異議に「影響度（高/中/低）」を付け、`.agent-reviews/redteam.md` にログを残す（フォルダがなければ作る）。観点の例：
   - 利用者が実際にはそう動かない（美容室スタッフ・非IT利用者の現実）
   - データが腐る経路（外部状態の変化、localStorage消失、Webhook不達）
   - 無課金構成の制約（レート制限・容量・停止）に将来ぶつかる
   - 更新運用が回らない（週次更新の手間、属人化）
3. **建設役**として高影響の異議を1つずつ処理する：修正して証拠で検証するか、「受容する理由」を明記する。
4. 批判役は、証拠のない回答を再オープンできる。**「説明しただけ」で解決扱いにしない。証拠必須。**

## 停止条件

- 高影響の異議が残っていない
- または同じ異議が**2ラウンド連続で新しい証拠なく**繰り返された（膠着として正直に記録して停止）

## 禁止事項

- 異議を潰しにくいからといって受容基準を緩めること
- 批判役が建設役に忖度すること（独立性を保つ）

## 報告形式

「確定した設計／解決済み異議（証拠付き）／受容した異議（理由付き）／膠着した点」。最後に、設計を変えた箇所を変更前後で対比して示す。
