# Renderproof 実物確認ループ

**中身が正しいことと、出力した実物が正しいことは別。** データ上は正しいセルに正しい値が入っていても、
枠に収まらない・行が割れる・ページが増える・重なって読めない、は中身の検査では検出できない。
このスキルは「実物にして目で見る」を、再現可能な手順に落とす。

## 適用の見分け方

**使う**：帳票・申請様式の自動記入、PDF/Excel/Word生成、印刷CSS、A4ページ数が要件になるもの、画像・図の生成。
**使わない**：画面上のWebアプリの操作性（→ uicheck）、単発のブラウザ操作やデバッグ（→ webapp-testing）。

## 手順

### 1. 控え（golden baseline）を先に用意する

変更前の出力を機械可読な形で保存し、**バージョン管理下に置く**。2回流して同一になることを確かめる
（同一にならないなら、時刻など揺れる項目を控えから外す）。これが無いと「直したつもりが別のところを壊した」を検出できない。

**控えの限界を必ず書き添える。** 例：「どのセルに何を入れたか」しか持たない控えは、
列幅・結合・書式の変更を検出できない。**控えの差分がゼロ＝安全、ではない。**

### 2. 実物として出力する

- **Excel/Word** — pywin32（`win32com.client`）で本物のアプリに開かせて PDF 化 → PyMuPDF（`import fitz`）で PNG
- **HTML/印刷** — Playwright（chromium同梱）または Chrome の `--print-to-pdf` → PyMuPDF で PNG。
  **ヘッドレスと実際の印刷ダイアログは一致しないことがある**（ヘッダーフッター予約・物理余白でページが1枚増える）。
  ページ高は物理上限ぴったりにせず余裕を持たせる
- **空の状態も同じ方法で出力し、並べて出す。** 記入後だけを見ても「元からそうなのか、こちらが崩したのか」は判断できない

### 3. 差分を「件数」ではなく「場所と値」で突き合わせる

変更前後で、どこに何を出力したかを全件比較する。**件数が同じでも出力先が変わっていることがある。**
「消えた」「増えた」が出たら、意図した変更かを必ず確かめる。

### 4. 並列で目視する（枚数が多いとき）

数十枚以上を1人で見るのは続かない。サブエージェントに分担させるときの縛り：

- **「どの画像の、どの項目が、どう見えるか」を必ず書かせる。**「問題ありません」だけの報告は無効としてやり直す
- **出力後と空を必ずペアで渡す。** 片方だけでは配布元・既定値の作りと自分の不具合を取り違える
- **「崩れあり」と挙がったものは、必ず自分でその画像を開いてから直す。** 伝聞で直さない（誤検出は実際に出る）
- 崩れが無かったぶんも、何枚見て何が入っていたかを書かせる。見ずに「問題なし」と書かれていないかはそこで分かる

### 5. 直したら、直した箇所だけでなく紙の全体を見る

**軽微な見た目を直しにいくときほど危ない。** 位置の微調整が、幅や既定値の解釈を壊して
行の途中で割れる・ページが増える、という重い崩れに化ける。
**ずれと、ページが崩れることは重さが違う。** 直す前と後で
「同じ出力が同じページ数に収まっているか」を先に確かめる。

### 6. 入れなかった側も見る

出力した箇所だけを検査すると「出力し損ねた」穴は永遠に見つからない。
**出力しなかった項目とその理由**を列挙する経路を別に用意し、両方回して初めて片側の見落としが消える。

## 停止条件

- 全出力について、控えの差分が説明でき、**実物の画像を目で見て**崩れが無いことを確認できた
- 2周連続で新しい崩れが出ない
- 直せない崩れは、**直さない理由を記録して**残す（配布元の仕様・要件との衝突など）。黙って放置しない

## 禁止事項

- 実物の画像を見ずに「崩れていません」と書く
- 控えの差分がゼロであることだけを根拠に「変わっていません」と書く（3.の限界を思い出す）
- サブエージェントの報告を自分で画像を開かずに信じて修正する
- 出力側だけを検査して「全部入っている」と書く

## 報告形式

「出力した実物の件数と方法／控えとの差分（場所と値）／目で見た枚数と見つけた崩れ（重大度順）／
直したものと、直さなかったものとその理由／ページ数など要件の前後比較」。
事実には**出所と観測時刻**を付ける。

## 引き継ぎ（次のセッションの自分のために）

このループの成果は、覚えていることではなく**書いてあること**でしか残らない。終わる前に：

- 点検コマンドを1つずつ、プロジェクトの引き継ぎ資料（`tools/README.md` 等）に書く
- **その資料へ誘導する1行を、プロジェクトの `CLAUDE.md` に置く。** 資料があっても、
  触る前に読ませる導線が無ければ次の自分は読まない
- 控えの**限界**（何を検出できないか）を資料に明記する
- 自動更新される入力（配布元の差し替え等）があるなら、**変わったことに気づく通知**を用意する。
  通知の本文に点検手順そのものを書いておくと、記憶が無くても手順が届く
